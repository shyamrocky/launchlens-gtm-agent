## Three decisions for owner review

Decision M15B3-001: **multilingual-e5-large as the first Pinecone-hosted baseline**.
Rationale: short focused inputs, public hash-pinnable tokenizer, existing Pinecone
support and no separate embedding provider. Its documented output is 1,024
dimensions/cosine and input ceiling is 507 tokens. This is a selection for review,
not a measured relevance winner. The earlier llama-text-embed-v2 suggestion was a
proposal, not an approved model; it remains an alternative with a longer window
that is unnecessary for the measured inputs. No broad model bake-off was run.
[Pinecone model specification](https://docs.pinecone.io/models/multilingual-e5-large).

Decision M15B3-002: **deterministic focused embedding projection**. Each existing
record gains a separate embedding_text in a new output. Product-claim register
prefixes (ID/status/source IDs) and requirement register prefixes are removed
mechanically from this view; redundant requirement section labels are removed.
Whitespace is joined, but substantive words, numbers and inline qualifications
are unchanged. Product name and document role are added as identifying context.
The original primary_text and every other original field remain inside the exact
evidence_payload. URLs in source-reference chunks remain if they are primary
content; this is not a blanket citation/URL deletion rule.

Decision M15B3-003: **co-locate the complete evidence with its future Pinecone
record**. The future embedded field is embedding_text only. Store the complete
original packet as a serialized string evidence_json, its SHA-256 and compact
flat identity/authority/provenance fields. Retrieve those fields with the hit (or
fetch the same record by ID), verify them and decode the full evidence. Related
claim IDs can be fetched from the same index if needed. No additional evidence
database, object store or local JSONL lookup is required by this design.

Pinecone metadata is flat and supports strings, with a 40 KB limit; a serialized
JSON string preserves the nested packet without pretending nested metadata is
supported. The largest measured escaped wire metadata is **21,357 bytes**, below
our conservative **40,000-byte** ceiling. No payload is cut to fit.
[Metadata format](https://docs.pinecone.io/guides/indexes/index-data-overview),
[operation limits](https://docs.pinecone.io/reference/api/database-limits/operation-limits).

## Tokenizer and local measurements

Public tokenizer: intfloat/multilingual-e5-large, revision
`3d7cfbdacd47fdda877c5cd8a79fbcc4f2a574f3`; tokenizers 0.22.2. The publisher model
card declares MIT. Only tokenizer.json, tokenizer_config.json,
special_tokens_map.json and README.md were fetched; hashes and sizes are pinned
in the maintained profile. No weights, remote model code, Transformers or PyTorch
were downloaded/executed. The model card specifies passage/query prefixes and
512-token architecture; the provider's stricter documented ceiling governs here.
[Pinned publisher files](https://huggingface.co/intfloat/multilingual-e5-large/tree/3d7cfbdacd47fdda877c5cd8a79fbcc4f2a574f3).

Local counting adds the passage prefix and two special tokens, disables truncation
and padding, and requires the complete count <=507. The upload-facing text itself
has no manual passage/query prefix; a future Pinecone adapter must use input_type
passage/query and truncate NONE, avoiding duplicate prefixes. Three example query
counts (20/14/16) are sample fit checks, not retrieval evaluations.

| Local measurement | Full-packet candidate | Focused projection |
|---|---:|---:|
| Total tokens, 45 passages | 38,974 | 4,275 |
| Largest passage | 1,384 | 279 |
| Passages over 507-token ceiling | 45 | 0 |

This is **89.03% fewer measured local input tokens**, not a billed-cost result or
proof of improved relevance. All 45 complete packets restore identically. Pinecone
does not expose an exact hosted revision in the cited model page: hosted tokenizer
parity and provider-reported token counts remain unverified. First separately
authorized embedding requests must confirm provider behavior with truncate NONE.

## Reproduce and storage boundaries

Root pyproject.toml/uv.lock are frozen inputs to accepted page manifests. A small
isolated tooling environment therefore provisions pypdf 6.21.4 and tokenizers
0.22.2 plus their locked transitive dependencies under tools/embedding_preparation/.
This preserves root dependencies and all accepted upstream hashes. No system-wide
install, inference framework or new hosted service is required.

From the repository root, with uv and an available Python 3.12:

```sh
uv sync --project tools/embedding_preparation --python .venv/bin/python --locked --no-python-downloads
uv run --project tools/embedding_preparation --locked python tools/prepare_embedding_projection.py --provision-tokenizer
uv run --project tools/embedding_preparation --locked python tools/prepare_embedding_projection.py
uv run --project tools/embedding_preparation --locked python -m unittest discover -s tools/embedding_preparation/tests -v
uv run --locked python -m unittest discover -s tests -v
```

The first command can use any existing Python 3.12 interpreter path; .venv/bin/python
is the existing project interpreter. In a new checkout first follow M1.5b.1/M1.5b.2
setup to recreate the root environment and page/chunk outputs, without changing
their locked dependencies. Tokenizer provisioning is the only network-enabled mode;
it fetches four exact public files with HTTPS verification and SHA-256/size checks.
Default projection/test execution is local. No .env or provider key is read.

Maintained tool, isolated profile/lock/template/tests and the standard-library
evidence codec in src/launchlens/evidence_payload.py are canonical. Regenerable
tokenizer cache is under ignored data/cache/; projection/audit outputs are under
ignored data/generated/m15b-embedding-projection/. These are documented build-time
inputs/outputs, not hidden runtime evidence storage. The future runtime gets its
packet from the Pinecone response; it does not open those local artifacts.
